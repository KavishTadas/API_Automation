 5. FRONT-END: WHAT IS DELIBERATELY *NOT* USED
================================================================================

 The unified console has ZERO third-party front-end libraries. Verified by
 inspection: the page contains exactly two <script> tags — one JSON data block
 and one inline script — and zero external network references.

   NOT used: three.js, motion.js, React, Vue, Angular, jQuery, D3, Chart.js,
             GSAP, Tailwind, Bootstrap, or any CDN.

 Everything below is hand-written instead:

 SVG (hand-authored)        Every chart — donut, trend line, module bars — and
                            the QA assistant figure. Drawn as SVG paths computed
                            from the run data.
 CSS 3D Transforms          The 3D depth. The assistant is 8 co-ordinate-aligned
                            SVG layers stacked in a preserve-3d container across
                            92px of depth; rotating it produces genuine parallax.
                            This is what a 3D library would otherwise provide.
 CSS Keyframe Animation     Hover, wave, orbit, thruster flicker, chart entrance,
                            pulse-glow and the donut sweep.
 CSS Custom Properties      Theming (light/dark), mood colours and the runtime
                            3D rotation values.
 Web APIs                   MutationObserver (re-decorates the report when it
                            re-renders), requestAnimationFrame (smooth motion),
                            localStorage (report history, preferences),
                            matchMedia (honours prefers-reduced-motion),
                            Pointer Events (the figure turns to face the reader),
                            Fetch (talks to the local harness).

 WHY THIS MATTERS FOR THE ORGANISATION
   - No supply-chain risk in the UI: nothing is downloaded at page load.
   - Works fully offline and behind a firewall.
   - A shared report is a single self-contained .html file that opens anywhere,
     with no server and no internet.

================================================================================
 7. ARCHITECTURE AND METHODS USED
================================================================================

 Seven-state result model     Every check resolves to exactly one of PASS, FAIL,
                              WARN, SKIPPED_NO_TOKEN, NOT_APPLICABLE,
                              NOT_ASSERTED or INFORMATIONAL. A request that
                              asserted nothing can never be counted as a pass.
 Honest pass rate             passRate = PASS / (PASS + FAIL), and is null — not
                              zero — when nothing ran. Results outside that
                              denominator are always shown alongside it.
 Stateless engine             API definitions travel by value in the run
                              manifest; the engine persists nothing between runs.
 Credential aliasing          A manifest names an alias, never a secret. Values
                              resolve at run time from .env or CI secrets.
 AST-based discovery          The catalogue is derived by parsing the test module
                              itself, so a new check registers automatically.
 Connection pooling           One reused HTTP client. Measured: 1156 ms/request
                              unpooled against 17 ms pooled.
 Circuit breaking             A host that fails to connect is remembered for the
                              rest of the run, so an outage costs one timeout
                              rather than one per check.
 Template-and-build           The console is generated from a template by a build
                              script; the built file is never hand-edited.
 Progressive enhancement      The motion layer is gated behind one attribute and
                              feature-detects every browser API, so the console
                              works fully with it switched off.
 Accessibility                Honours prefers-reduced-motion; live regions are
                              announced; all controls are keyboard-focusable.

 8. CI/CD AND ENVIRONMENT
================================================================================

 GitHub Actions        .github/workflows/api-tests.yml — checks out, installs
                       Node 24 and Python 3.11, generates the inventory and the
                       test suites, runs the tiers, builds the Allure report and
                       uploads it as an artifact.
 actions/setup-java    The CI pipeline installs Java because allure-commandline
                       requires a JVM to build the browsable report.

 ACTION REQUIRED — Java is NOT installed on this development machine.
   Consequence: `npm run report:generate` (the browsable Allure report) will not
   run locally. Everything else — the Python tier, Newman, the unified console
   and all 7 UI suites — works without it, and CI is unaffected because the
   pipeline installs its own JVM. Install a JDK 11+ if local Allure reports are
   needed.

================================================================================
 9. HOW TO INSTALL EVERYTHING
================================================================================

   python -m pip install -r requirements.txt      # runtime dependencies
   python -m pip install -e ".[dev]"              # pytest, Allure, schema tools
   npm ci                                         # all Node tooling

 Run:
   python -m harness.serve                        # then open /console
   npm run ui:test                                # the 7 UI suites
   npm run test:uat                               # the Postman collections
